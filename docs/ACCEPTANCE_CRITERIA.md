## 1. 判定方法

目的は、設備を操作して、同じ気象条件で環境・牛の放熱・参考影響の違いを理解できること。
実農場との一致、投資回収、全設備から受胎への新たな換算は合格条件にしない。
乳量は[仮説モデルv0.1](MILK_HEAT_MODEL_V0_1.md)の受入条件MH01〜MH15を追加する。
新モデルの実装と検証対応は上記実装報告に記載。以下の旧コード対応だけを新モデルの合格判定として使わない。
実装担当は[実装計画・引継ぎ](MILK_MODEL_IMPLEMENTATION_PLAN.md)のP0〜P6と検証手順を使用する。

- **対応あり**：画面から計算・結果へ至るコードを確認した。動作合格を意味しない。
- **一部不足**：経路はあるが、条件に必要な表示や説明が不足している。
- **未実装**：現在計画に追加した条件で、既存の表参照・60分計算では満たさない。
- **要確認**：コードだけでは操作性・表示・実行環境での成否を判定できない。
- テストIDは既存テストの所在を示す。今回、単体・統合・ブラウザ試験は再実行していない。
- 2026-09-27の調査で実行したのは `npm run typecheck`（成功）。2026-09-28の文書更新では再実行していない。過去の62件・21件の合格記録を現行版の合格判定へ転記しない。

具体的な表示方法や操作の割り当ては本書の提案。乳量の式・係数・時間については仮説モデルv0.1を参照する。

## 2. 最初に通す利用経路

1. 標準牛舎と基準案の設備・共通気象を確認する。
2. 編集案Aで屋根対策を変更し、同じ地点の環境と放熱の差を見る。
3. ファン・ソーカー・ミストを追加または移動し、影響する場所を確認する。
4. 基準案・A・Bを切り替え、同じ地点・時間集計で結果を比較する。
5. 乳量・受胎の参考影響と、その適用条件を確認する。
6. 変更を戻す、別案へコピーする、保存して再開する。

初期Aは基準の複製。初期Bは同じファンでソーカー停止・ミスト稼働。
基準はファン10台＋ソーカー12個が稼働し、屋根対策なし。無設備との比較ではない。

## 3. 設備ごとの操作契約

「配置」は位置を持つ設備へ適用する。屋根対策は牛舎全体への設定とする案。
屋根の部分塗装・断熱材の部分配置・屋根ノズルの個別配置は、今回の必須条件に加えない。

| ID | 設備 | 受入条件：操作と期待結果 | 現行対応・試験 |
|---|---|---|---|
| EQ01 | 遮熱 | ON/OFFと反射率変更ができる。変更は編集案だけへ反映され、屋根裏温度・放射環境・局所気温・放熱を再計算する | 対応あり。ONで0.7、OFFで0.2。詳細は0〜1。V08-PY2、R01、I01、E02 |
| EQ02 | 断熱 | ON/OFFと厚さ変更ができる。屋根表示の開閉と計算設定を区別する | 対応あり。ONで20mm、OFFで0。詳細は0〜0.1m。V08-PY3、R01、E02・E14 |
| EQ03 | 屋根散水 | ON/OFF、面積あたり流量、ON/OFF周期、日運転時間を変更し、熱環境と水・電力量へ反映する | 対応あり。全屋根への設定。V08-PY4、R02、E18 |
| EQ04 | ファン | 追加・選択・複製・削除・有効化、移動、座標・高さ・向き・下向き角・出口風速・運転時間の変更ができる。位置による風速と放熱の違いを見る | 対応あり。Store・UI・3D/2Dに経路あり。UT03/04、IT03/05、E03〜E05・E16。現行3Dでの実操作は要確認 |
| EQ05 | ソーカー | ノズル追加・複製・削除・配置・有効化、流量・噴霧角と系統の周期・運転時間を変更できる。捕水・保持水・蒸発による放熱と水量を比較できる | 対応あり。UT09、UT11/12、IT06、E07。追加から結果までの専用E2Eは不足 |
| EQ06 | ミスト | ノズル追加・複製・削除・配置・有効化、流量・噴霧角と系統の周期・運転時間を変更できる。局所気温・湿度・放熱と資源量を比較できる | 対応あり。UT13〜16、E06。追加から結果までの専用E2Eは不足 |

共通の注意：

- ノズル個別の有効状態と系統のON/OFFは別。停止系統へ追加しただけでは稼働しない。利用者がこの状態を判別できることを確認する。
- ファン追加で外気との空気交換量を自動増加させない。風速の変化と換気量の仮定を区別する。
- 設備の移動だけでは日水量・日電力量を変えない。稼働条件の変更は資源量へ反映する。
- 全操作で必ず改善することは要求しない。届かない位置や同一条件では差がないことも正しい。
- 上限は各案40ファン・ソーカーとミスト合計100ノズル。上限時は状態を壊さず説明する。最大構成の応答性は未確認で、秒数の基準は未設定。

## 7. 受入確認で使う具体的なシナリオ

| 手順 | 操作 | 合格時に確認すること |

| 1 | 新規起動、基準とAを比較 | 50床・70評価点、Aは同条件で放熱差0。基準は無設備ではない |
| 2 | Aで遮熱と断熱をON | 基準設備は保持。標準条件で屋根裏温度等と放熱差が変わり、全地点を再計算。新モデルの日負荷・日乳量・差が同じ24時間条件から得られる |

| 4 | AをBへコピーし、片方だけファンを追加・移動 | 変更前の条件が揃い、位置・風速・放熱差を比較できる。移動だけで日資源量は増えない |
| 5 | ソーカー／ミストを別々に追加・移動し、系統をON/OFF | 捕水・保持水または局所温湿度の変化と資源量が対応。系統停止時に「追加したのに効かない」理由が分かる |

| 8 | Undo/Redo、保存、変更、再読込、不正JSON読込 | 正常保存は復元・再計算。不正読込では現在案を保持し、内部例外を出さない |

3. **現行版の受入試験を整える**：Three.jsでの主導線再確認、ソーカー／ミストの追加から結果への専用確認、地点切替と表示値の照合。既存E2Eは生成済みHTMLを読むため、ソースと配布物の対応を確認してから実行する。
