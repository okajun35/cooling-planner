## 1. 結論

二択なら「既存コードを使う」。ただし、現行画面へ機能を継ぎ足すのではなく、**画面とモデルをつなぐ処理を組み直し、独立している計算・幾何・編集状態管理を再利用する**ことを推奨する。

全面的な書き直しを勧めない理由は、現在のソースにDOMや描画ライブラリから分離された計算、設備配置、ドラッグのトランザクション、Undo/Redo、JSON検証、古いWorker結果の拒否があり、今回の再実行でも既存テストが通ったため。過去に工数をかけたからではなく、今の目的にも必要な機能が実装されていることが理由である。

一方、現在の画面、結果データ、比較案の操作はv0.4のファン・ソーカー・ミスト比較に合わせている。屋根・乳量・受胎・時間表示を継ぎ足すだけでは旧構成が残る。**新UIと新しい統合処理は作るが、計算や編集の仕組みまでゼロから書き直さない。**

## 5. 作り直す・拡張する部分

### 5.1 画面と表示構成

`main.ts`は画面テンプレート、入力イベント、結果カード、全地点表、保存UI、Worker起動をまとめている。現在の主カードは「参考放熱差・風速・水・電力」であり、気温等は詳細欄にある。

操作中心の画面へ組み替える際は、環境入力、設備パレット、選択設備、3D、結果、時系列を別の部品へ分割する。カードを増やすだけにはしない。

**屋根表示のチェックは描画だけの設定**で、遮熱塗装の有効／無効ではない。新しい屋根対策設定を独立して持つ。

### 5.2 ドメイン型・比較案・保存形式

現在の`Environment`に日射入力はなく、`Scenario`は`fans`と`waterSystems`だけを持つ。`waterSystems`はソーカー・ミストに限定されている。

必要な拡張：

- 共通環境：屋根面日射など、v0.5の入力。
- 案ごとの屋根：反射率、断熱材、屋根散水。
- 参照モデル：基準乳量、受胎の基準確率・期間代表条件と由来。
- 結果：屋根／空気／放射、送風体感温度、熱の時系列、乳量・受胎の状態付き参考値。
- 保存：新しい形式版と計算モデル版、係数・仮定。

現行`validation.ts`は3案、案ID、2水系統を厳密に固定している。保存・検証・比較操作も新しい型に合わせて一括変更する。入力欄だけ増やして終わりにしない。

旧JSONを無条件に新モデルとして再計算したことにはしない。対応するなら明示的変換、初版で対応しないなら旧版を残し、新形式のみを受け付ける。これは新しい物理モデルを作る話ではなく、実装上の保存契約の整理である。

### 5.3 シミュレーション実行順序

現在は環境温度・固定放射条件を用い、設備のON/OFFパターンごとに計算をまとめている。平均と最終水収支を返すが、グラフ用の時系列は返していない。

新しい統合処理では、案ごとの屋根／空気時系列を求め、それを地点別の風速・ミスト・体表水へ渡す。屋根水膜が変化するため、現在のON/OFFだけのメモ化をそのまま屋根に適用しない。

熱モデルは60分のまま。乳量は掲載条件と静的条件を判定し、対象外はnull。受胎は別の期間代表条件を持たせる。時間や適用範囲の決定をやり直さない。

### 5.4 入力ハッシュとキャッシュ

`simulation.ts:13–16`の`scenarioInput()`は、現在`fans`と`waterSystems`だけを抽出する。`72–73`行の同一案キャッシュにも同じ関数を使う。

**案ごとに`roof`を追加する場合、屋根条件もハッシュとキャッシュキーへ必ず含める。** さもないと、屋根の異なる2案を同一計算と誤認する。これは現行仕様の不具合ではなく、新モデルを統合するときの変更必須箇所である。

### 5.5 描画

配布版は独自WebGLレンダラー。標準ビルド用の`threeBackend.js`は存在するが、現時点のThree.js用アダプターは同じ三角形／線分データを描く方式で、切り替えただけでビジュアルが大きく変わる構成ではない。

描画上の所見：

- 牛と建物はプリミティブの簡略形状。
- 色の表示は70評価点の円盤が中心。
- `particles`という設定は現状では散水範囲の線の表示。
- 0〜60分の計算時系列の再生UIはない。

表示は、簡略3Dのままでも設備と熱の変化が分かる方向で組み直す。生成画像の写実性を完成条件に追加しない。

環境制約のための独自バンドラー／WebGL版と標準Vite／Three.js版を、新アプリで永続的に二重保守することは勧めない。標準ビルドが確認できる環境でThree.js側へ一本化し、旧配布版は変更前の確認用として残す。

## 7. 実装の方針案

既存コードのスナップショットを残し、新しいブランチ／作業ディレクトリで整理する。新しいリポジトリや大規模なモノレポを作ることは要件にしない。

```text
app / ui                    新しい入力・設備操作・結果・時間表示
  └─ shared project state   既存Storeを拡張
      └─ simulation worker  既存のジョブ管理を再利用
          ├─ layout / wind / capture       v0.4再利用
          ├─ psychrometrics / cow film     v0.4再利用
          ├─ roof / barn air               v0.5参照実装を移植
          ├─ milk reference                v0.6仕様を実装
          └─ fertility reference           v0.7参照実装を移植
      └─ 2D / 3D views      計算値を読む。計算式を持ち込まない
```

Python参照実装を使うためだけにAPIサーバーを追加する必要はない、という実装方針を推奨する。計算はTypeScriptへ移植し、Worker内にまとめる。Python側の係数JSON・計算例・テストケースを照合用として残す。移植後は同じ入力で双方の結果を比較する。

最初に通す経路は「屋根対策変更→屋根／空気／放射→牛の放熱→対策前後表示→保存・復元」。その経路を残したまま、設備移動、散水周期、乳量参照、受胎シナリオを接続する。

旧ブラウザ試験はセレクターを更新する必要があるが、検証する振る舞いは引き継ぐ。全画面完成後に初めてテストを移すのではなく、1経路ごとに移す。

## 8. この評価で増やさないもの

- 新しい牛舎形式や、つなぎ牛舎への対応。
- 乳量表の補間・外挿。
- 全対策を乳量・受胎へ必ず換算するモデル。
- 実牛舎の実測検証、CFD、牛の生理の完全再現。
- 52日間の秒単位計算、気象予測API。
- ログイン、管理画面、課金、汎用シミュレーション基盤。

**完成済みとしたモデルの判断は戻さない。残りは再構成・実装・統合確認である。**
