# 時刻別気象と制約付き案比較の実装計画

作成：2026-10-01。対象はCooling Plannerの③制約付き探索、④時刻別気象。別モデルへ渡す実装引継ぎ案。
状態：計画のみ。以下はPOC向けの提案仕様であり、現行版の実装済み機能ではない。実装担当はユーザーから着手依頼を受けて進める。

## 1 実装順序と完成イメージ

**④時刻別気象と日単位の場所別集計 → ③MCPによる少数候補の制約比較**の順に実装する。

「冷却設備の水を1,000 L/日以内にして、牛床の不足を減らしたい」と依頼すると、同じ代表日・同じ設備台数で運転条件などを変えた少数案を計算し、条件を満たす候補と残る不足を比較できるようにする。選んだ案は既存のJSON読込で画面に戻せる。

ハッカソンPOCなので、探索はLLMが候補を作り、既存モデルが数値と制約判定を返す構成にする。汎用最適化ソルバー、常駐ジョブ、データベース、気象API、共有リンクは今回追加しない。モデル係数・乳量換算式の校正も行わない。

実装単位はA〜Cの3つ。各単位で動く状態を引き継ぐ。

| 単位 | 内容 | 終了時にできること |
|---|---|---|
| A | 24時間気象入力と日熱集計 | 夜間日射0を含む代表日で、放熱不足・水・電力を同じ24時間にそろえて計算 |
| B | 日比較の画面とMCP接続 | 日平均の場所別不足を確認し、JSONで同じ条件・数値を再現 |
| C | 制約付き候補比較 | 数案を条件付きで比べ、理由と残る不足を添えて選択案を画面へ渡す |

まずA・Bを完了させる。Cの候補生成方法は、Aで実測した処理時間を見て小さく調整する。

## 2 現行実装から引き継ぐもの

- `src/model/dailySimulation.ts`：準備24時間＋評価24時間。屋根水・牛体の保持水を引き継ぎ、設備の日運転枠を適用する。現状は気象を固定し、主に牛群加重の不足と日乳量を返している。
- `src/model/dailySchedule.ts`：日跨ぎの運転、日運転開始時刻でのON周期再開。今回もこの規則を使う。
- `src/model/simulation.ts`：固定条件60分の診断と入力ハッシュ。既存の60分診断を保持する。
- `src/model/comparisonStats.ts`：平均だけでなく最大・残る不足を比較する。現状の入力は60分結果なので、そのまま日結果として扱わない。
- `src/mcp/commands.ts`、`aws/lambda/core.ts`：ローカル／リモートで共有する操作と評価。`evaluate`の返す`project`をJSONで画面に戻せる。
- `src/ui/comparison.ts`、`src/ui/projectImport.ts`：案比較、場所の確認、JSON貼付を再利用する。

実装前に作業ツリーと最新のAGENTS.mdを読む。別担当がレイアウトを作業している場合は、画面の骨組み・CSSの変更を必要最小限にする。

## 3 単位Aの気象入力

### 入力する値

Projectへ`dailyWeather`を追加する。気象の正本はこの項目と既存`environment`に置き、乳量専用設定の中に時刻表を重複保存しない。

| 項目 | 提案仕様 |
|---|---|
| mode | `constant` または `hourly`。初期値はconstantで現行結果を維持 |
| hours | hourly時は0〜23時の24行。各行のhourは一意で昇順 |
| 各行の物理値 | `temperatureC`、`relativeHumidityPct`、`solarRoofWm2` |
| 共通の値 | 気圧・背景風速・換気量は既存environmentを全時間で使う |
| 時刻 | 既存設備スケジュールと同じ代表日の時計。暦・タイムゾーン変換・夏時間は扱わない |
| 区間 | 0時行は00:00以上01:00未満。1時間内は一定値。補間しない |
| 繰り返し | 準備日と評価日で同じ24行を反復 |

入力範囲は当面既存モデルの検証範囲（気温20〜40℃、湿度0〜100%、屋根面日射0〜1,200 W/m²）を継承する。日射は屋根面の入力であり、水平面日射を無変換で測定値として採用しない。欠損行・重複時刻・非有限値は通常の入力エラーとし、自動補間・丸めはしない。

hourlyモードでは夜間の日射も明示入力で決まる。場所と日付から日の出を推測する処理は追加しない。デモに夜間0を設定して、利用者が変更できる形にする。

### 画面の最小構成

既存の気象パネルから「日計算の気象」を開き、固定／時刻別を選べるようにする。時刻別は24行×3項目の表で編集する。「固定値を24行へコピー」と「仮の昼夜例」の2操作を用意する。入力をまとめて適用した時点で1回再計算し、1セル変更のたびに48時間計算を走らせない。

仮の昼夜例は次の値を各時刻へ展開する案とする。**デモ用の設計仮定であり、観測値・気象予報ではない。**

| 時刻 | 気温℃ | 湿度% | 屋根面日射W/m² |
|---|---:|---:|---:|
| 00〜05時、19〜23時 | 26 | 80 | 0 |
| 06〜08時 | 28 | 75 | 150 |
| 09〜16時 | 32 | 60 | 600 |
| 17〜18時 | 29 | 70 | 100 |

初回起動時にこの例へ自動切替はしない。ユーザーが選んだ場合に適用し、保存時もデモという説明を残す。

## 4 単位Aの日熱計算

### 時刻切替と状態の引継ぎ

気象取得の純粋関数を追加し、日計算へ現在時刻の環境を渡す。物理式は既存の`solveRoof`、`heatTerms`、`filmStep`、`mistAir`を使う。

実装上、次の箇所を忘れずに更新する。

1. 現在ループ外で計算している外気水蒸気圧`pv`と乾いた屋根`dryRoof`を、気象区間ごとに更新する。
2. 区間をまとめて計算する`dur`を、次の気象切替時刻でも分割する。設備が動かなくても気象が変われば更新する。
3. `prevAvail`による屋根再利用、`memoSeq`による熱伝達再利用を気象変更で無効にする。同じ保持水量でも日射・温湿度が違えば再計算する。
4. 毎時・0時・準備日終了で屋根水や牛体保持水を初期化しない。日運転周期の開始規則も既存どおりにする。
5. シナリオを変えるたびに同じ初期条件からその案の準備日を計算する。別案の準備終了水量を流用しない。

屋根・空気は現行の熱容量を持たない縮約モデルのままなので、時刻境界で環境値が段階的に変化し得る。この点を仕様に明記する。時間刻み・レイ数を減らす近似は今回追加しない。

### 日結果の契約

`ScenarioResult.dailyThermal`を追加し、熱の日比較を乳量カードから独立して取り出せるようにする。新しい熱計算を二重に実行する必要はなく、既存日ループで同時に集計する。

- 評価期間86400秒、気象モード、モデル版、計算状態と理由。
- 全70地点の`meanDeficitW`と`meanQrefW`。不足は毎秒`max(0,Qref−Q)`を計算してから積算し、平均Qから作らない。
- 各地点の日平均風速・気温・湿度、対流・放射・蒸発・結露の内訳。局所作用割合は既存の「その地点で作用した秒数」の定義を継承し、単なる設備ON時間で代用しない。
- 全地点と牛床／採食／待機の平均不足、最大の地点平均不足、不足上位地点。各区域は代表点の単純平均。
- 評価日の水・ファン電力・ポンプ電力。既存`dailyResources`を使い、準備日の消費を含めない。

各地点の累積値だけを保持し、48時間×70地点の秒系列は保存しない。24時間グラフ・瞬間最大値・新しい乳量時系列は初版に含めない。

牛群の滞在割合で加重する既存の`dailyDeficitWPerCow`と、配置診断の70地点単純平均を区別する。乳量は同じ秒別不足から既存重みで求め、係数・上限・同日反復のE=Dを維持する。受胎を時刻別気象から自動更新する機能は追加しない。

## 5 単位Bの保存と画面とMCP

### 保存形式

計算入力の意味が変わるので、保存形式10、統合モデル版`cooling-integrated-v0.10`を提案する。乳量仮説モデルIDと熱の基礎式のIDは維持する。

v9の既存案を使えるように、**v9→v10だけ**の小さな読込変換を作る。旧environmentを固定気象として引き継ぎ、設備・係数・基準案は保持する。v8以前と未知の将来版は既存同様に拒否する。変換後は入力ハッシュが変わるが、固定気象の数値結果は変わらないことを確認する。

- JSONファイル・貼付・端末内復元・リモートMCPで同じ読込変換を通す。APIだけ旧版を拒否する状態を避ける。
- `dailyWeather`は計算入力ハッシュへ含める。表示期間の選択はViewへ置き、物理ハッシュに含めない。
- `milkSimulation.weatherMode`は日気象から決まる互換用項目として同期・検証する。気象を二箇所から独立編集させない。
- defaults、保存キー、Worker、例JSON、MCP説明、生成HTML名とREADMEの版表示を同じ変更単位で更新する。旧配布HTMLは残してよい。

### 表示期間をそろえる

比較画面に「60分診断／1日比較」の切替を置く。1日比較では案カード・エリア表・床の色・選択地点の不足と内訳を`dailyThermal`へそろえる。日集計が未着・失敗なら日比較は計算中／未評価とし、60分値を代わりに表示しない。

日画面で用意していない詳細項目は省略する。既存の60分グラフには「固定条件60分」の表示を保ち、1日結果の再生と誤解させない。60分用environmentと日気象表の役割を気象パネルに示す。

`evaluate(includeDaily:true)`と`get_results`へ日熱結果を追加する。日計算のWorker応答・`mergeDaily`・結果ゲートを更新し、途中で条件が変わった場合に旧結果が混ざらない既存経路を使う。MCP操作には全案共通の`update_daily_weather`を追加し、24行をまとめて適用する。

## 6 単位Cの制約付き候補比較

### POCでの探索の分担

LLMが変更範囲と候補を組み立て、MCPが入力を検証して熱・資源・制約結果を計算する。まず1回の会話で最大12案程度を比較する。これは応答時間を抑える運用上の目安で、モデル精度を表す数値ではない。

新ツールは`compare_candidates`の1つに絞る。1回に1〜3案の操作列を受け取り、同じ開始projectの複製へそれぞれ適用する。前の候補の変更が次の候補へ累積しないようにする。候補を増やす場合も、同じ開始project・同じ制約で分けて呼ぶ。

既存`evaluate`は汎用の感度試行用として維持する。候補比較の内部では既存の日計算と操作関数を共有し、探索候補すべての60分診断まで繰り返す必要はない。開始案の日結果は1呼出し内で再利用してよい。永続キャッシュや再開ジョブは作らない。

### 変更を許す範囲

初版の既定は**既存設備の運転調整だけ**とする。候補間で気象・牛舎・Qref・モデル係数・乳量係数・滞在割合を固定する。ファン台数・ノズル数・定格電力・出口風速も固定し、数値を有利にするために設備性能を書き換えない。

| 範囲 | 初版の扱い |
|---|---|
| ファン | enabled、日運転時間、開始時刻を候補化可能 |
| ソーカー／ミスト／屋根散水 | enabled、ON/OFF秒、日運転時間、開始時刻を候補化可能 |
| 配置・向き | ユーザーが指定した場合だけ、既存ファン／ノズルの少数の具体的位置・向きを比較 |
| 遮熱・断熱 | ユーザーが屋根変更を許した場合だけ、明示した設定を候補に含める |
| 台数追加・機種変更・流量性能 | 初版の自動候補化対象外。必要なら利用者が開始案を編集してから比較 |

`compare_candidates`で許可した操作・フィールドを確認する。`update_model`、`update_milk`、`update_environment`、気象表変更、基準案切替、別案へのコピーは候補操作に使わない。Project全体を候補として自由に差し替える入力形式にもせず、既存の編集可能案1つへ操作列を適用する。

### 制約と比較基準

| 入力 | 意味 |
|---|---|
| maxWaterLPerDay | 冷却設備全体の供給水上限。ソーカー・ミスト・屋根散水を合計。飲水・洗浄水は対象外 |
| maxElectricityKwhPerDay | 任意。ファンとポンプを合わせた日電力量上限 |
| priorityArea | 牛床・採食・待機・全地点。初期提案は牛床 |
| protectAreas | 開始案より日平均不足を増やさない区域。既定は牛床・採食・待機すべて |
| protectWorst | 開始案より全地点最大の日平均不足を増やさない。既定true |

保護条件が厳しすぎて候補がなくても、LLMが無断で緩和しない。どの条件が候補を除外したかを示し、利用者が比較の優先順位を変更できるようにする。

改善の目標・保護条件の基準は**探索を始めた編集案**とする。既存の固定baselineとの差も別欄で保持し、「基準案との差」と「探索開始案との差」を混同しない。

水・電力は表示前の数値で制約判定する。数値誤差の扱いは既存積算の誤差範囲だけとし、表示の丸めで超過を合格にしない。日計算が無効な候補は未評価として除外し、0不足・0消費にしない。

### 最初の候補の作り方

まず開始案を評価し、水の上限を超えているか確認する。散水の運転時間やOFF時間を段階的に変えた3〜4案を作り、次にそのうち有望な条件とファン運転の組合せを少数試す。数値は既存の入力範囲・刻みに収める。任意台数の配置を総当たりする探索は作らない。

水・電力の上限を確実に超える案は`dailyResources`で先に除外できる。資源条件を満たした案は、実際の日熱計算で効果と保護条件を判定する。水半減から効果半減を推測するなど、未計算案の順位付けはしない。

### 出力と選び方

各候補についてID、適用操作、開始入力ハッシュ、候補入力ハッシュ、評価状態、日資源、区域別平均不足、最大不足、悪化地点数、制約違反理由を返す。`constraintsSatisfied`と`improvesPriorityArea`を分け、条件は満たすが効果がない案も区別する。

比較関数は重み付きの不透明な総合点を作らず、次の順序で並べる。同順位は候補ID順にして再現可能にする。

| 提示案 | 条件を満たす候補の順位付け |
|---|---|
| 不足低減優先 | 優先区域の平均不足 → 最大不足 → 水 → 電力の小さい順 |
| 節水優先 | 優先区域が開始案より改善する候補に絞り、水 → 優先区域不足 → 電力の小さい順 |
| 悪い場所優先 | 最大不足 → 優先区域不足 → 水 → 電力の小さい順 |

同じ候補が複数で1位なら重複して3案に見せず、1案と理由を返す。複数呼出しの結果はLLMが同じ規則で比較し、評価した候補一覧を添える。各呼出しの順位はその呼出し内だけの順位であることを返値へ明記する。

条件を満たす案がない場合は「今回評価した候補では見つからない」と返す。全探索していないので実現不可能とは断定しない。処理失敗・未評価があればその数も示す。

利用者が選んだ候補は、開始projectへその操作列を適用した`evaluate(includeDaily:true)`で最終確認し、返値のprojectをJSONで渡す。Viewの表示期間を1日比較にしておけば、読み込んだ画面でも探索時と同じ指標を確認できる。

## 8 最小限の検証と引継ぎ

実装担当は必要な計算テストを先に追加し、型チェック・関連する単体／統合テスト・ビルドを実行する。モデル入力と日集計を変えるAではthermalのPython参照テストも実行する。受胎を変更しない今回、fertilityの再実行は必須にしない。全E2Eの実行は人間とCIに任せる。

追加テストは次の6観点に絞る。大量の画面条件やテスト専用フレームワークを増やさない。

1. 全24行が同じなら現行固定気象の日結果と一致する。旧v9案の変換後も数値が一致する。
2. 時刻境界・23時→0時で正しい行を選び、途中の気象変更で熱結果が変わる。昼夜切替で屋根水・牛体水が維持される。
3. 不足を先に切り詰めてから日平均する。例：不足200 Wが12時間、0 Wが12時間なら100 W。日平均Qから不足を計算する誤実装を検出する。
4. JSON復元とMCPで気象表・入力ハッシュ・日結果が一致し、未対応版は現在案を保持する。
5. 上限超過を除外し、平均改善に隠れた区域／最大不足の悪化を保護条件で検出する。invalidは合格にしない。
6. 候補間で操作が累積せず、気象・係数・設備性能は固定。順位・重複候補の扱いと、候補0件の返答を確認する。

人間／CIには次の3操作を依頼する。

- 仮の昼夜例を適用し、1日比較で水・電力と区域別不足が出る。
- MCPで水上限付きの数案を比較し、上限超過や残る不足の説明が読める。
- 選んだ案のJSONを読み込み、1日比較の配置・数値を確認してUndoできる。

処理時間は標準配置の1案を1回、候補3案を1回測ればよい。実際の配置で遅すぎる場合は1呼出し1案へ減らす。計算精度を落としたり、先に非同期基盤を作ったりしない。既存Lambdaの設定はリポジトリ上180秒だが、MCPクライアント側の待ち時間もあるため、上限まで使える前提では設計しない。

実装報告には完成した単位、使い方、実行した軽量テスト、未実施の人間／CI確認、追加したデモ仮定、ソースと公開版の反映状況を短く記載する。コミット・公開は、その時点のユーザー指示に従う。
